# Clover storefront order visibility — live

The existing Clover Online Ordering storefront remains the live ordering system. This change adds a **read-only** section to Nazar's private `/staff/crm` screen. Staff explicitly loads recent orders; the server uses the existing `crm_staff_authorized_v1` allowlist before requesting Clover. The browser never receives a Clover token. The response contains only Clover order ID, time, order type, and total. It does not copy customer contact details into Nazar's CRM or claim that a Clover order came from the Nazar website.

## Activation prerequisites

1. Nazar's production merchant dashboard created **Nazar CRM order visibility** on October 16, 2026. **Talip's October 20 statement** is that its current permissions are **Orders → Read, Payments → Read, and Customers → Read**; Clover's merchant token panel has no separate Refunds checkbox. This permission list is **panelde doğrulanacak** (pending confirmation in the merchant dashboard), not an independently verified panel record. The token value is stored as a Cloudflare Pages **Production** secret `CLOVER_ORDERS_ACCESS_TOKEN`; it was not copied to the repository or Preview environment. Clover's published developer guidance describes merchant-level tokens mainly for direct sandbox access and recommends expiring OAuth tokens for production apps. If production API access fails, investigate the exact request and token permissions before considering an OAuth integration or a token change; neither is authorized by this note.
2. The verified production merchant ID **`F8Q154GMDKFD1`** is stored as `CLOVER_MERCHANT_ID`. The Clover October order-type report shows online **Delivery `NAJM24T7CQC1R`** and **In-store Pickup `912777FPE4SM4`**, separated from Clover Devices order types; these are stored as comma-separated `CLOVER_ONLINE_ORDER_TYPE_IDS`. All three are server variables, not `VITE_` browser variables.
3. On October 16 the production CRM returned the October 15 test delivery order **`VC9D60CHEKW4M`** exactly once, with **$44.53**. An anonymous API request returned `unauthorized`. A separate POS sale exclusion and unlisted-account test still need live confirmation.
4. If the read fails or reaches a page limit, use Clover Orders as the source of truth and investigate. The panel explicitly marks partial results. No customer order-history linkage, marketing attribution, or new-order alert is implied by this view.

The Clover Orders dashboard and notification showed this order as paid, while its REST order `paymentState` returned `OPEN` and `state` returned `locked`. The merchant dashboard's Transaction details showed $51.52 collected, versus $44.53 returned in the REST order `total`. The CRM labels that figure as the order amount, omits the unreliable status fields, and links directly to the matching Clover order so staff can confirm actual payment and fulfillment there. Without the secrets/configuration, the panel says the connection is not set up. No database migration is required.
