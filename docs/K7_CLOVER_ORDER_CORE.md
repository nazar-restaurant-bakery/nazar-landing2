# K7 — Clover order core operator notes

Apply `supabase/migrations/20261020000700_clover_order_core.sql` with **psql 18.6** and `ON_ERROR_STOP=1`, first to Nazar-catering-sandbox and later to production only after Talip's approval and successful test. Use the identical LF file and record its SHA-256. The file adds only private `core` tables and narrow RPCs; it never changes marketing consent.

The pull is manual: an authenticated CRM staff session sends `POST /api/staff/clover-order-pull` with JSON `{"days":1}` and the same-origin `Origin` header. Days must be 1–30. There is no scheduler or browser-supplied business/merchant identity. Preview requires its **own** isolated `TEST_` Clover merchant ID, Orders Read token, online order type IDs, and existing sandbox Supabase settings. It cannot fall back to production credentials. Production uses existing `CLOVER_MERCHANT_ID`, `CLOVER_ORDERS_ACCESS_TOKEN`, and `CLOVER_ONLINE_ORDER_TYPE_IDS` settings. Talip manages all keys and account actions.

Production token record, October 20, 2026: Talip states that **Nazar CRM order visibility** has **Orders → Read, Payments → Read, and Customers → Read** enabled in the Clover Merchant Dashboard; there is no separate Refunds checkbox there. **Panelde doğrulanacak:** this is Talip's report, not an independently checked permission snapshot. The October 16 “Orders Read only” record describes the token at creation and is no longer the stated current permission list. The Preview test token is separate and must not be inferred from these production permissions.

The earlier 403 on a single-order request with `expand=refunds,customers` does not prove which expansion Clover rejected. Clover documents both as expandable order fields and maps API reads by data category, so a permission check associated with either field is one possible explanation. Another possibility is that an edited merchant token's effective scope did not match the panel selection at request time. Clover documents viewing/editing merchant-token permissions, but does **not** state there whether editing requires a new token; its reinstall/new-token instruction concerns **app permissions after installation**, so it cannot establish a regeneration rule for this merchant token. These remain hypotheses until the post-#66 live result separates the `refunds` and `customers` requests. [Single-order expansions](https://docs.clover.com/dev/reference/ordergetorder-3) · [Permission mapping and app reinstall scope](https://docs.clover.com/dev/docs/gdp-set-app-permissions) · [Merchant-token permissions](https://docs.clover.com/dev/docs/gdp-create-merchant-specific-api-token).

For each order, Clover must return line items, payments and order type. A missing payment collection stops the pull rather than treating an unknown payment as zero. Refund and customer reads run separately: denied refunds leave the day's refund total unconfirmed, and denied customers leave the order without a customer match; neither is silently treated as a verified zero. A partial database failure returns `pull_unconfirmed`; rerun the same window because Clover IDs are unique and upserted. The handler returns aggregate counts only, never customer data.

Read the review queue through `clover_order_match_queue_v1(business_id)` as authenticated CRM staff. Resolve a row with `clover_order_match_resolve_v1(business_id,review_id,customer_id)`; pass a null customer ID to leave it unlinked. The closed-day reconciliation RPC `clover_order_day_totals_v1(business_id,start,end)` returns order count, paid order count, paid, refunded and net cents. Choose start/end to match Clover's exact report time zone and population; a disagreement blocks acceptance. `core.clover_order_status_v1` derives status only from the stored payment/refund rows and cancelled state.
